## Исходное описание
«Есть замечание к коду, в коде есть различные секреты, которые не должны попасть в публичный репозиторий. Настрой и
исправь это, также добавь .ignore, чтобы подготовить репозиторий к публикации в удалённый репозиторий»

## Цель
Гарантировать, что в публикуемом репозитории (рабочая копия и история) нет секретов и персональных данных сверх
решения пользователя, и что секреты не попадут туда в будущем: полный `.gitignore`, шаблон конфигурации без секретов,
документация «где хранить секреты» и автотест-сканер, входящий в `dotnet test`.

## Сценарии
1. Разработчик клонирует репозиторий, кладёт ключ Context7 в `.claude/settings.local.json`, токен бота — в
   user-secrets, создаёт `deploy/multibot.env` для сервера → `git status` не показывает ни одного из этих файлов.
2. Кто-то по ошибке вставляет токен бота в `appsettings.json` или в документацию → `dotnet test` падает с
   указанием файла, строки и правила, не печатая сам токен.
3. Новый участник читает README «Секреты и конфигурация» и знает, куда класть каждый ключ локально и на сервере.

## Критерии приёмки
Все проверки, использующие git, **не зависят от глобальных настроек пользователя**: глобальные исключения
(`core.excludesFile`, `~/.config/git/ignore`) нейтрализуются (например, `git -c core.excludesFile=<пустой временный файл>`;
способ выбирает tester). Иначе тест зелёный у автора и красный/ложно-зелёный у других.

- **AC-1 (игнорируются).** Given корневой `.gitignore` и `webapp/.gitignore` из BE-1/BE-2 и нейтрализованные
  глобальные исключения, When для каждого пути ниже выполняется `git check-ignore --no-index`, Then каждый путь
  игнорируется:
  `.claude/settings.local.json`, `.env`, `.env.local`, `.env.production`, `deploy/multibot.env`, `foo.env`,
  `src/Bot.Host/appsettings.Local.json`, `src/Bot.Host/appsettings.Development.local.json`, `secrets.json`,
  `certs/server.pfx`, `certs/server.p12`, `certs/server.pem`, `certs/server.key`, `keys/strong.snk`, `msbuild.binlog`,
  `logs/app.log`, `npm-debug.log`, `coverage/index.html`, `.vscode/settings.json`, `src/Bot.Host/data/bot.db`,
  `bot.db-journal`, `webapp/.env.local`, `webapp/.env.production.local`, `webapp/coverage/index.html`,
  `webapp/vite.log`, `out/app/Bot.Host.dll`, `.DS_Store`.
- **AC-2 (не игнорируются).** Given те же условия, When `git check-ignore --no-index` для путей ниже, Then ни один не
  игнорируется: `.gitignore`, `.mcp.json`, `src/Bot.Host/appsettings.json`, `src/Bot.Host/Properties/launchSettings.json`,
  `deploy/multibot.env.example`, `.env.example`, `webapp/.env.example`, `.vscode/extensions.json`,
  `.claude/settings.json`, `.claude/agents/architect.md`, `webapp/public/telegram-web-app.js`,
  `webapp/package-lock.json`. **And** ни один отслеживаемый файл не подпадает под правила игнорирования
  (`git ls-files --cached --ignored --exclude-standard` пуст).
- **AC-3 (в репозитории нет секретов).** Given множество «файлов-кандидатов» = отслеживаемые + неотслеживаемые
  неигнорируемые (`git ls-files --cached --others --exclude-standard`, с нейтрализованными глобальными исключениями;
  удалённые с диска и бинарные — нулевой байт в первых 8 КБ — пропускаются), When сканер применяет правила R1–R5
  (см. «Правила сканера»), Then находок нет, кроме записей allowlist. Allowlist изначально **пуст**.
- **AC-4 (сканер работает).** Given образцы строк/файлов, When сканер их проверяет, Then:
  - помечаются (по одному образцу на правило минимум): токен формата Telegram (`<9 цифр>:<35 символов [A-Za-z0-9_-]>`);
    ключ `ctx7sk-` + 36 символов `[0-9a-f-]`; заголовок PEM приватного ключа — с типом (RSA) и без типа
    (пять дефисов, `BEGIN`, необязательный тип, `PRIVATE KEY`, пять дефисов);
    JWT из трёх сегментов `eyJ….eyJ….…`; в `*.json` — `"Token": "abc123"`, `"WebhookSecret": "s3cr3t"`,
    `"CONTEXT7_API_KEY": "anything"`; в `*.env`/`*.env.example` — `Bot__Token=abc`, `Bot__WebhookSecret=abc`;
  - **не** помечаются: `123456:TEST-TOKEN`, `654321:ANOTHER-BOT-TOKEN`, `test-webhook-secret`,
    `distinct-secret-value-xyz`, 64-символьный hex (hash initData), `"${CONTEXT7_API_KEY}"`, `Bot__Token=<токен>`,
    `Bot__Token=` (пусто), `"Token": ""`, R5-образец в `*.md`/`*.cs`/`*.ts` (R5 только для конфигов),
    ключи `package-lock.json` вида `"node_modules/js-tokens": {`.
  Образцы, совпадающие с R1–R4, **собираются в рантайме** (конкатенацией), а не лежат литералом в исходнике: файл
  тестов сам проходит AC-3 без allowlist.
- **AC-5 (сообщение не раскрывает секрет).** Given найденная строка, When тест падает, Then сообщение содержит
  `путь:строка` (путь относительно корня репозитория, `/`-разделители) и id правила (`R1`…`R5`), а совпавшее значение
  не выводится (ни полностью, ни частью длиннее 4 символов).
- **AC-6 (шаблон конфигурации).** Given `deploy/multibot.env.example`, Then он содержит ровно те ключи, что блок
  `/etc/multibot/multibot.env` в `DEPLOY_CHECKLIST.md` (после правки BE-4 — ссылка на шаблон), секретные значения
  (`Bot__Token`, `Bot__WebhookSecret`) — заглушки вида `<…>`, остальные — значения по умолчанию из чек-листа; файл
  проходит AC-3. Проверка автотестом: множество ключей шаблона = множество ключей из таблицы README
  «Секреты и конфигурация» с пометкой «сервер» (BE-3).
- **AC-7 (документация).** README содержит раздел «Секреты и конфигурация» по BE-3. *Проверка — ревью critic*
  (содержательный текст автотестом не проверяется; исключение из правила «каждый AC — автотест», см. реестр).
- **AC-8 (история).** Given вся история (`git log --all -p`), When разово прогоняются правила R1–R4 и
  `git log --all --oneline -- .claude/settings.local.json '*.env' '*.pfx' '*.pem' '*.key'`, Then находок нет и
  перечисленные пути ни разу не коммитились; список уникальных идентичностей `автор/коммиттер` выведен в отчёт.
  *Разовый аудит tester, результат — в отчёте, не автотест* (историю переписывает оркестратор после закрытия спеки; после перезаписи проверка идентичностей повторяется —
  см. «Принятые решения»).

## Правила сканера
Ищутся только **форматы реальных секретов**, а не слова «token/secret» в коде — иначе ложные срабатывания на
тестах и спеках.

| ID | Что | Где | Признак (инвариант, регекс — на усмотрение tester) |
|---|---|---|---|
| R1 | Токен бота Telegram | все файлы | 8–10 цифр, `:`, ровно 35 символов `[A-Za-z0-9_-]`, по краям не `[A-Za-z0-9_-]` |
| R2 | Ключ Context7 | все файлы | `ctx7sk-` и далее ≥ 20 символов `[A-Za-z0-9-]` |
| R3 | Приватный ключ | все файлы | заголовок PEM: пять дефисов, `BEGIN`, пробел, необязательный тип ключа (заглавные буквы и пробелы), `PRIVATE KEY`, пять дефисов |
| R4 | JWT / bearer (TMDB v4 и т.п.) | все файлы | `eyJ…` три base64url-сегмента через `.`, каждый ≥ 10 символов, первые два начинаются с `eyJ` |
| R5 | Секрет, присвоенный в конфиге | `*.json` (кроме `package-lock.json`), `*.env`, `.env*`, `*.env.example`, `*.ini`, `*.conf`, `*.yml`, `*.yaml`, `*.toml` | ключ, последний сегмент которого (после `:`, `__`, `.`) без учёта регистра равен `Token`, `Secret`, `WebhookSecret`, `ApiKey`, `API_KEY`, `CONTEXT7_API_KEY`, `Password`; значение — строковый скаляр (не `{`, `[`, число, `true/false/null`), непустой и не заглушка. Заглушка = целиком `<…>` или `${…}` |

Allowlist — в коде теста: запись = (путь, ID правила, причина). Добавлять запись можно только для доказанно
несекретного совпадения и с перечислением в `DEVIATIONS` отчёта.

## Принятые решения (ответы пользователя)
- **Объём — вариант A:** ключ Context7 (`.claude/settings.local.json` — в проектный `.gitignore`) + общая гигиена
  (`.gitignore`, шаблон, документация, автотест-сканер). Тестовые фейки остаются без изменений.
- **История git — вариант A «переписать автора»:** до первого push автор и коммиттер во **всех** коммитах заменяются
  на публичную идентичность (имя + noreply-email хостинга; конкретные значения пользователь даст отдельно) через
  `git filter-repo` (mailmap), затем задаются `user.name`/`user.email` на уровне репозитория. Шаг **вне кода**:
  выполняет оркестратор с согласия пользователя после закрытия спеки (critic = `APPROVED`), не разработчики и не
  tester. Порядок:
  1. все коммиты задачи 006 сделаны (включая незакоммиченные правки пользователя — их судьбу решает пользователь до
     перезаписи; перезапись требует чистой рабочей копии);
  2. перезапись истории и настройка `user.name`/`user.email` репозитория;
  3. повторная проверка AC-8 по идентичностям: в `git log --all --format='%an <%ae>%n%cn <%ce>'` остаётся только
     публичная идентичность, исходные ФИО/email не встречаются ни в одном коммите и ни в одной ссылке (`--all`).
  До перезаписи TEST-6 только фиксирует список идентичностей в отчёте (исходные ФИО/email в нём ожидаемы).

## Принятые решения архитектора / допущения
- Номер 006 — эта задача; рефакторинг «сценарии групп в Application» → 008 (007 — «CI/релиз и процесс через pull request»).
- `appsettings.Development.json` **не** игнорируется: секретов в appsettings нет по правилу проекта (user-secrets),
  а сканер R5 поймает нарушение. Игнорируются только явно локальные `appsettings.Local.json`, `appsettings.*.local.json`.
- Шаблон — `deploy/multibot.env.example`, а не корневой `.env.example`: .NET не читает `.env`, имя `.env.example`
  вводило бы в заблуждение; шаблон соответствует `EnvironmentFile` systemd.
- Сканер — тест xUnit в `Bot.Platform.Tests`, без внешних инструментов (gitleaks) и без нового тестового проекта.
- Тестовые фейки не переименовываются: они не совпадают с форматом R1, сканер явно проверяет их как негативы.
- `.vscode/settings.json` пользователя игнорируется (личные настройки), общий `.vscode/extensions.json` — допустим.
- Спека сама проходит AC-3 без allowlist: образцы R1–R4 в ней описаны словами, а не литералами. Allowlist остаётся
  пустым (запись для этой спеки, добавленная tester, удаляется).
- R5, уточнения (по реализации tester, приняты): числовое значение и `true`/`false`/`null` не считаются секретом
  только в `*.json`/`*.yml`/`*.yaml`/`*.toml` (там это типизированные скаляры); в env/ini/conf все значения —
  строки, поэтому `Bot__Token=12345` — находка. Строки-комментарии (`#`, `;`) в env/ini/conf не разбираются как
  присваивание R5 (R1–R4 к ним применяются). Поддерживаются префикс `export KEY=...` и несколько пар
  ключ–значение в одной строке JSON.
- `.git/info/exclude` (локальные исключения репозитория) не нейтрализуется: он не переносится при клонировании и
  у чистого клона пуст; нейтрализуются только глобальные исключения.
- AC-6/TEST-5: ключ README считается серверным, если ячейка колонки «Сервер» начинается с «да» (без учёта
  регистра); формат таблицы README это обязан соблюдать.
- DEPLOY_CHECKLIST §2: отдельный шаг `chmod 600`/`chown root:root` после `install -m 600 -o root -g root`
